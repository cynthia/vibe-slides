# Transcript: Harnesses and Multi-Agent Orchestration

## Slide 1: Harnesses 101
When people first see a coding agent, the easy mistake is to think the model itself somehow became an engineer. It did not. What actually changed is the control loop around the model: what it can see, what it can do, what gets remembered, and what gets blocked. The little pipeline on this slide is the important one for the rest of the talk: model, harness, tools, workspace. If you remember only one thing from this first section, remember that the harness is where token prediction turns into behavior with consequences.

## Slide 2: What Is an LLM?
At the bottom, an LLM is doing something almost embarrassingly simple: it predicts the next token. Then it appends that token, looks at the new sequence, and does it again. A polished answer, a shell command, or a wild hallucination are all just long chains of locally plausible next steps. The token strip on the slide is there to make that feel concrete, because "intelligence" in this setting is built from many tiny probability decisions. Sometimes that is humbling, and sometimes it is also a useful debugging lens.

## Slide 3: The Transformer Makes It Work
The transformer changed the game because each prediction can attend across the available context rather than marching forward with a tiny memory. In a causal LLM, the model gets to ask, "which earlier parts of this sequence matter for what I am about to say now?" That is why code completion, translation, and long-form explanation all became dramatically better. The annoying part is the small grid on the right: self-attention compares pairs of token positions, so the cost grows roughly with the square of sequence length. When someone says, "just give it a bigger context window," the engineer in the room should hear, "thank you, I have purchased a larger bill and a new reliability problem."

## Slide 4: Tokens, Context, and Sampling
Models do not read characters the way humans do; they read tokens, which are chunks that may be words, fragments, punctuation, or code pieces. That means your budget is shared by everything in the session: the prompt, file contents, tool output, previous mistakes, and the answer you hope to get. Sampling parameters matter because they change how conservative or adventurous the model is when choosing the next token. Low temperature is the model wearing a tie; high temperature is the model improvising jazz in production. On the right, the curves are there to show that we are not just asking for an answer, we are choosing how much randomness we want in the search.

## Slide 5: How Models Are Built
This slide is useful because it separates capabilities that often get blended together in conversation. Pre-training gives you broad pattern recognition over a huge corpus, which is why the model can finish code, imitate styles, and explain concepts. Mid-training or domain adaptation sharpens particular skills, like code, math, or long-context behavior, where raw pre-training is not enough. Then post-training teaches the product behavior we actually interact with: follow instructions, call tools in the right format, avoid obviously bad behavior, and generally act like an assistant instead of an autocomplete engine. By the time a model reaches users, it is already a stack of training choices plus deployment constraints, not a pure research artifact.

## Slide 6: Base Model to Agent
So how do we get from a base model to something that looks agentic? We add instruction-following behavior, tool-call formats, a system prompt that defines role and policy, and then a harness that enforces what is real versus what is merely requested. This is an important distinction: the model can ask to run a command, but the harness decides whether that command happens, where it happens, and what comes back. That is why two products built on similar underlying models can feel completely different in practice. Agent behavior is as much systems design as model behavior.

## Slide 7: What the Harness Owns
Here is the core loop in operational form. The harness owns the message history, exposes the available tools, executes tool calls, and decides when to stop, retry, or escalate. In other words, the harness is the traffic cop and the blast shield. If the model proposes something unsafe, the harness is the thing that says, "absolutely not," ideally before the filesystem learns a valuable lesson. That boundary matters because the model is generative, but the harness is where policy becomes enforceable.

## Slide 8: SFT Teaches Tool Use
Tool use does not appear by magic the first time a model sees a JSON schema. During supervised fine-tuning, the model is shown transcripts where a user asks for something, the assistant emits a structured tool call, the tool returns a result, and the assistant grounds its final answer in that result. Over many examples, the model learns not just the syntax, but the rhythm: when to call a tool, how to chain calls, and how to stop guessing once evidence arrives. That is why transcript quality matters so much. If the harness appends noisy, ambiguous, or lossy tool results, we are feeding the model bad lessons at inference time.

## Slide 9: Single-Agent Harnesses Hit a Ceiling
Now we can talk about where the single-agent pattern starts to crack. One agent has one context window, one evolving line of reasoning, and one role trying to hold the entire task together. If it makes an early bad assumption, that mistake does not just disappear; it becomes part of the working memory for the rest of the session. You can often feel this failure mode when an agent becomes confidently committed to the wrong frame and keeps digging. Bigger models help, but one long trajectory is still one long trajectory.

## Slide 10: One Context Window Is Not a Plan
This is the part where people point to giant context windows and say the problem is solved. More capacity is useful, but capacity is not control. A model can be shown the right file, the wrong file, three logs, a tool schema, and a previous bad plan all in the same prompt, and nothing forces it to attend to the right pieces in the right order. The large box on the slide is intentionally cluttered because that is what real sessions look like. If the only coordination strategy is "put everything in one stream and hope," inspection and reliability both get ugly very quickly.

## Slide 11: Long Inputs Degrade Attention in Practice
Benchmarks back up that intuition. Needle-style tests are a clean way to ask whether the model can retrieve a specific fact buried somewhere in a long context, and performance often depends quite a bit on where that fact is placed. Broader benchmarks like LongBench show that the problem is not limited to toy retrieval; it spills into summarization, question answering, few-shot tasks, and code. So yes, longer context helps, but it does not abolish attention cliffs or confusion. The heatmap on the slide is really a picture of why "it fit in the prompt" is not the same thing as "the model used it well."

## Slide 12: Long Agent Chains Accumulate Errors
Tool-using agents add a second problem on top of long context: state keeps changing. Every tool call can inject new observations, new artifacts, or new misunderstandings into the transcript. Once a bad assumption becomes part of that history, later steps often rationalize around it instead of correcting it. Recent work on multi-turn degradation makes this uncomfortable point quite clearly: reliability can get worse as the conversation grows, even when the model is capable in a cleaner single-turn setting. So the failure is often not that the model cannot do the task, but that the interaction pattern slowly poisons the run.

## Slide 13: Decomposition Is the Escape Hatch
The obvious response is decomposition. If a task is too messy to solve well in one pass, split it into smaller subproblems, give each subproblem the context it actually needs, and only pass forward the parts that matter. Models are surprisingly good at proposing this structure, which is why least-to-most prompting and Tree of Thoughts feel like early hints of a bigger systems pattern. The DAG on the slide is the key shape: branch where independence helps, merge where synthesis is required. Once you see that, a single giant agent loop starts to look less like intelligence and more like queueing all your technical debt into one chat transcript.

## Slide 14: Multi-Agents and Ensemble Inspiration
This brings us to the main claim of the talk: multi-agent systems are a kind of test-time ensemble with tools, roles, and memory boundaries. The point is not to create more chatter. The point is to preserve diversity long enough to get better work, then synthesize that work explicitly instead of pretending one trajectory was always enough. The fan-out and merge picture on the slide is intentionally simple because the high-level pattern is simple. The hard part is making the orchestration disciplined rather than theatrical.

## Slide 15: Classical Ensemble Ideas Map Cleanly
I like borrowing language from classical machine learning here because it keeps us honest. Bagging maps pretty naturally to repeated samples or parallel agents whose errors are not perfectly correlated. Boosting looks like staged correction, where later passes focus on weaknesses from earlier ones. Mixture-of-experts shows up as specialization and routing: send architecture questions to one role, verification to another, and synthesis to something that can fuse the results. The analogy is only useful if it drives real design choices, but when it does, it gives us a much better vocabulary than "just add more agents and vibes."

## Slide 16: Voting Beats One Guess When Errors Differ
Self-consistency made a very simple point that turned out to matter: if you sample multiple reasoning paths and the errors differ, selecting the most consistent answer often beats taking the first guess. Multi-agent work extends that idea by instantiating several workers rather than several hidden chains in one model. The key phrase is "when errors differ." If all workers are wrong in the same way, congratulations, you have built a parallelized mistake. But when the task admits different solution paths, automated parallel attempts can buy you accuracy surprisingly cheaply.

## Slide 17: Specialization Beats One Generalist
Voting is not enough for engineering work because outputs are often partially right rather than cleanly right or wrong. That is where specialization helps. One model or role may be better at architecture, another at detailed implementation, another at ranking or fusing candidate answers. Systems like LLM-Blender and mixture-of-agents are interesting because they preserve multiple candidates long enough to compare and merge them, instead of collapsing early. On the slide, the synthesizer is doing the adult job of the team: not choosing one person to be correct, but assembling the strongest pieces into a coherent result.

## Slide 18: Debate and Collaboration Add Friction on Purpose
There is a reason so much agent research keeps rediscovering branching, critique, and externalized reasoning. Straight-line generation is fast, but it commits early. ReAct adds evidence gathering, Tree of Thoughts adds branching search, and multi-agent collaboration turns some of that internal deliberation into explicit work products from separate workers. That added friction is not inefficiency for its own sake. It is how we create chances to catch a bad direction before it hardens into a finished answer with very confident formatting.

## Slide 19: Small Contexts Can Beat One Long Context
So why can several smaller contexts outperform one huge one? First, each agent sees less junk and has a narrower checklist, which reduces competition for attention. Second, disagreements become visible because different workers expose different assumptions instead of blending them into one monologue. Third, the synthesis step forces us to decide what survives into the shared narrative. The warning label is the last bullet on the slide: if synthesis is sloppy, the team just generates more text and more confusion. This is why orchestration quality matters more than agent count.

## Slide 20: finb Design Decisions
Everything from here is about how I tried to operationalize those ideas in finb. I built it with a fairly pessimistic worldview: agents will break things, lie to themselves, and occasionally discover creative new ways to waste context. So the design posture became straightforward. Make damage cheap, make the work inspectable, keep synthesis explicit, and do not hard-wire the system to one vendor or one harness. If that sounds less romantic than "autonomous intelligence," that is because I wanted something I could trust on a bad day.

## Slide 21: Design Around Failure
This slide is the tradeoff triangle that motivated the system. Full lockdown is safe, but the human becomes the throughput bottleneck because every meaningful action needs approval. Full YOLO mode is fast, right up until the model enthusiastically deletes the wrong tree and teaches you humility. I wanted the middle path: give the agent room to act, but make the blast radius reversible. In practice, that means optimizing for controlled failure rather than pretending we can eliminate failure.

## Slide 22: Safe-to-Destruct Workspaces
The concrete mechanism is safe-to-destruct workspaces. Each agent runs in a copy-on-write ZFS snapshot, and rollback is effectively cheap enough to treat destruction as a routine control mechanism rather than a disaster. Chroot keeps the agent constrained to the filesystem it is supposed to see, without needing to make containers or full VMs the center of the architecture. I like this design because it moves the question from "can the agent be trusted?" to "can the system recover instantly when it should not have been trusted?" In my experience, that is a much more realistic systems question.

## Slide 23: Agent Teams Are a DAG
Once isolation was handled, the next design choice was execution structure. finb treats a team run as a phased DAG rather than one giant conversation with multiple names in it. Within a phase, tasks can run concurrently; between phases, the system synthesizes what matters and hands that forward. This keeps dependencies explicit and makes it much easier to inspect why some later decision happened. Hidden state is convenient until you need to debug it, at which point it becomes folklore.

## Slide 24: Mailbox Turns Agents Into a Team
The mailbox is the coordination primitive that made the whole thing feel like a team instead of parallel strangers. Agents can send mail to named teammates, and that mail gets delivered in the next phase as visible prompt context. That means coordination is explicit, attributable, and auditable later. I care about that because "the agents somehow knew" is not an explanation, it is a horror story. A mailbox is boring, which in systems design is often another word for good.

## Slide 25: Synthesis Has Influence Tiers
One lesson from early runs was that synthesis needs structure, not just summarization. So finb uses influence tiers: one primary agent owns the final narrative, supporting agents shape major sections and constraints, and contributing agents supply evidence, checks, or edge cases. The reason for a single primary is simple: without it, the final answer can drift into a committee document that offends everyone equally. At the same time, attributed synthesis is still useful when you want to preserve disagreement or provenance. So the system keeps both unified and attributed modes available.

## Slide 26: Iteration Keeps the Team Moving
Another practical lesson is that good work often appears on the second pass, not the first. finb treats iteration as a first-class loop: take the current deliverable, feed it back into planning, spin up fresh agents with fresh context, and retry only the pieces that failed. That last part matters because long runs should not require replaying everything from scratch when one worker falls over. Checkpoints and re-entry points are not glamorous, but they are the difference between a demo and a usable system. I built this because I got tired of losing promising progress to brittle one-shot sessions.

## Slide 27: Harness-Agnostic Architecture
The last design point is architectural humility. finb is not trying to replace every underlying harness; it is trying to orchestrate them. So the TUI handles interaction and visibility, the orchestrator owns planning and synthesis, the agent manager handles process lifecycle, and the harness layer maps onto concrete tools like Claude Code, Gemini CLI, or whatever comes next. That separation buys portability and keeps the orchestration logic from being fused to one provider's product assumptions. If the bottom layer changes next month, and it will, I would like the rest of the system not to have an emotional breakdown.

## Slide 28: Example Results
These examples were the point where I stopped thinking of the system as an interesting control surface and started thinking it might actually be useful. `termnes` produced a terminal NES emulator in Rust, with real subsystem boundaries like CPU, PPU, rendering, input, and mapper logic. `at3rs` tackled ATRAC3, which is not exactly the domain I would choose for a casual demo if my goal were to sleep peacefully. `sloppng` built a PNG-focused tool with binary parsing and validation instead of just spraying cheerful boilerplate at the filesystem. None of these are "write me a sorting function" tasks; they are the kind of multi-file, integration-heavy builds where I genuinely did not expect agent teams to get as far as they did.

## Slide 29: What the Results Demonstrate
What these runs demonstrate is not magic, and that is exactly why I find them interesting. Planning agents can break down a hard project into phases that specialist implementers can attack independently. Verification and review passes catch integration bugs that a single linear generation often leaves behind, and synthesis turns parallel effort into one codebase rather than a folder full of competing truths. The real product is coordinated execution under rollback, not more generated prose. If you asked me a year ago whether a team of agents could build a terminal NES emulator well enough to make me raise an eyebrow, the honest answer would have been "only if the eyebrow was expressing concern."
